# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`index.html` is a single-file Kanban-style IT project management demo for a fictional "UOB IT PMO" (internal training tool — not a real UOB system; no real UOB logo/trademarks, text wordmark and corporate-blue palette only). It is vanilla HTML/CSS/JS with no dependencies, no build step, and no backend beyond a FormSubmit AJAX call for email notifications.

## Running / testing

There is no build, lint, test, or package tooling in this repo (no `package.json`, no bundler). The entire app is `index.html`.

- **Run it**: open `index.html` directly in a browser (double-click, or `open index.html` on macOS). No local server required.
- **Syntax-check the inline script** after edits: extract the `<script>...</script>` body and run `node --check` on it, e.g.
  ```bash
  awk '/<script>/{f=1;next}/<\/script>/{f=0}f' index.html > /tmp/check.js && node --check /tmp/check.js
  ```
- **Verify `getElementById` references stay in sync with HTML ids** after edits (a common breakage point since there's no compiler to catch typos):
  ```bash
  grep -oE "getElementById\('[^']+'\)" index.html | sed "s/getElementById('//;s/')//" | sort -u > /tmp/used.txt
  grep -oE 'id="[^"]+"' index.html | sed 's/id="//;s/"//' | sort -u > /tmp/defined.txt
  comm -23 /tmp/used.txt /tmp/defined.txt   # should print nothing
  ```
- There is no headless-browser tooling (no `chromium-cli`, `playwright`, or `puppeteer`) installed in this environment — visual verification requires opening the file in an actual browser.

## Hard constraints (do not violate when editing)

These are deliberate product constraints, not oversights — preserve them unless the user explicitly asks to change them:

- **Vanilla only**: no React/Vue/jQuery/Tailwind, no build step, no npm, no frameworks.
- **Single file**: all markup, one `<style>` block, and one `<script>` block live in `index.html`. Don't split into separate CSS/JS files.
- **No external resources**: no CDN scripts, no Google Fonts, no external images. Icons are inline SVG or Unicode glyphs; fonts are the system font stack (`--font-stack` custom property).
- **No persistence**: board state is an in-memory JS object only. Never introduce `localStorage`, `sessionStorage`, `IndexedDB`, or cookies — a page refresh is *supposed* to reset the board to seed data, and the header displays a note saying so.
- **No real branding**: text wordmark "UOB IT PMO" only, corporate blue palette — never a real UOB logo/trademark.

## Architecture

Everything is state-driven and re-rendered from a single source of truth:

```js
const state = { tasks: [], filters: { project, assignee, priority }, ui: { confirmDeleteId } };
```

- **Render flow**: `renderBoard()` is the only place that rewrites card DOM. It filters `state.tasks` through `applyFilters()`, then for each of the four fixed statuses (`STATUSES` array: Backlog/In Progress/Blocked/Done, each with a DOM-id `slug`) rebuilds that column's `.card-list` via `renderCard()` and updates its count badge, then calls `renderSummary()` for the header stats strip. No code should mutate a card's DOM directly outside this path — mutate `state`, then call `renderBoard()`.
- **Events are delegated**, not attached per-card, because cards are destroyed/recreated on every render: `initDragAndDrop()` and `initCardActions()` attach one set of listeners to `#board` (and to the four static `.column` elements for `dragover`/`dragleave`/`drop`) and dispatch on `data-action`/`data-id` attributes read from `e.target.closest(...)`.
- **Drag-and-drop** uses the native HTML5 DnD API (`draggable`, `dragstart`/`dragover`/`drop`) with a `.drag-over` class toggled on the hovered column. The **keyboard-accessible fallback** is a per-card `<select data-action="move">` — both paths funnel into the single `moveTask(taskId, newStatus)` function.
- **Delete confirmation** is inline state, not `confirm()`: clicking delete sets `state.ui.confirmDeleteId` and re-renders; the card then shows Yes/No buttons wired to `deleteTask()` / clearing the id.
- **Add Task flow** (`initAddTaskForm()`): `validateForm()` returns `{valid, errors}` and errors are written into per-field `<span class="field-error">` elements (no `alert()`). On success it's optimistic: `addTask()` pushes into `state.tasks` and re-renders immediately, a success toast fires synchronously, and `notifyNewTask()` (the FormSubmit call) runs in parallel — its failure only produces a warning toast and never blocks or reverts the UI. Task IDs are generated by `nextTaskId()` as `UOB-ITPM-####` from a module-level `idCounter` (seeded to the count of demo tasks).
- **FormSubmit integration**: `FORMSUBMIT_ENDPOINT` is the one config constant at the top of the `<script>` block (currently `https://formsubmit.co/ajax/nikitarst3@gmail.com`) — change the address there only. FormSubmit requires one-time email activation: the first submission to a given address sends that address a confirmation email, and no submissions deliver until the link in it is clicked. `notifyNewTask()` is always called from a `.catch()`/`try-catch` path so a FormSubmit failure can never break board state.
- **Dates**: `todayISO()` / `isoDateOffset(days)` compute local-timezone `YYYY-MM-DD` strings (avoiding UTC off-by-one from `toISOString()`). `isOverdue(task)` is `status !== 'Done' && dueDate < todayISO()`. Seed data (`seedTasks()`) generates its due dates via `isoDateOffset()` relative to whenever the page loads, so the "Overdue" demo badge is always correct regardless of when the file is opened.
- **Security**: `escapeHtml()` must wrap every user-supplied string (title, description, assignee — free text fields) before it's interpolated into an HTML template string in `renderCard()` or elsewhere. There is no other sanitization layer.
